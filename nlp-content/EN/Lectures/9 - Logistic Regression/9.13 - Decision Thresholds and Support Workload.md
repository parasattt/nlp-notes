## Choose a threshold for the support team's costs

The team wants negative reviews to reach support. Missing an angry customer costs more than spending time reading an extra positive review.

A probability lets us set the decision ourselves. Instead of always using “negative if `P(negative) > 0.5`,” try another threshold. Lower thresholds flag more reviews. This is the precision/recall trade-off from Lecture 7, now applied to complaints rather than spam.

The code gets the negative-class probability from column 0. `is_negative` marks the true complaints. At each threshold, it counts all flagged reviews, the fraction of complaints caught (**recall**), and the fraction of the support queue that really is negative (**precision**).

The spam-filter example in [[EN/Lectures/7 - Naive Bayes Classification/7.8 - Confusion Matrices Precision and Recall|Confusion Matrices Precision and Recall]] has different error costs, so it emphasises a different side of the same trade-off.



```python
from sklearn.metrics import precision_score, recall_score

lr_proba = cross_val_predict(setups["LR  + tf-idf"], reviews, y_all, cv=cv5, method="predict_proba")
p_negative = lr_proba[:, 0]
is_negative = (y_all == "negative")

print("threshold | sent to support | recall (angry customers caught) | precision")
for t in [0.5, 0.45, 0.4, 0.35]:
    flagged = p_negative > t
    print(f"   {t:.2f}   |      {flagged.sum():3}        |             "
          f"{recall_score(is_negative, flagged):.2f}               |   "
          f"{precision_score(is_negative, flagged, zero_division=0):.2f}")
```

The plot checks 81 thresholds from 0.3 to 0.7. It shows recall, precision, and the share of all reviews sent to support, so the workload cost stays visible beside the metrics.

```python
thresholds = np.linspace(0.3, 0.7, 81)
rec = [recall_score(is_negative, p_negative > t) for t in thresholds]
prec = [precision_score(is_negative, p_negative > t, zero_division=0) for t in thresholds]
sent = [(p_negative > t).sum() / len(p_negative) for t in thresholds]

plt.figure(figsize=(6.5, 3.4))
plt.plot(thresholds, rec, label="recall: angry customers caught")
plt.plot(thresholds, prec, label="precision: queue that is really negative")
plt.plot(thresholds, sent, ls="--", color="grey", label="share of all reviews sent to support")
plt.axvline(0.5, color="black", lw=0.8)
plt.text(0.505, 0.05, "default 0.5", fontsize=8)
plt.xlabel("threshold on P(negative)")
plt.title("Moving the threshold moves errors, it does not remove them")
plt.legend(fontsize=8)
plt.tight_layout()
plt.show()
```

Lowering the threshold grows the support queue. The saved table moves from 60 flagged reviews with recall 0.68 and precision 0.68 at threshold 0.50, to 117 flagged with recall 1.00 and precision 0.51 at 0.35.

There is no universally correct threshold. The decision depends on the cost of missing a complaint compared with the time cost of reading an extra positive review. The probability model makes that choice explicit.

The costs here are substantial: catching 95% of negative reviews at threshold 0.40 sends 102 of all 120 reviews to support. The threshold is working, but the model is weak. Moving it changes which mistakes we accept; it does not add new evidence or improve the underlying ranking. The source phrases this as moving error types rather than removing them.

Because many probabilities cluster near 0.5, a small threshold change moves many reviews at once, creating the steep middle of the plot. The larger-data example later shows a different confidence range.
