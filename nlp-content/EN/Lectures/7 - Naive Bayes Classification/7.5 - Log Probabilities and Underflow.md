## Very small products and underflow



This loop prints the growing product after every four words and at the end. Its purpose is to show the numerical scale, rather than to train a new model.

```python
long_message = "free money click now win cash prize urgent claim your free prize now today"

score = p_spam
for i, w in enumerate(long_message.split(), 1):
    score *= p_smoothed(w, spam_counts, len(spam_words))
    if i % 4 == 0 or i == len(long_message.split()):
        print(f"after {i:2} words: {score:.3e}")
```


**Saved output:**

```text
after  4 words: 1.441e-05
after  8 words: 1.384e-10
after 12 words: 1.772e-15
after 14 words: 2.746e-18
```



Every multiplication is by a probability below 1, so the product rapidly becomes smaller. The saved example ends after 14 words at `2.746e-18`. The original explanation says thirteen words reach $10^{-19}$; that does not match the saved example, but both illustrate the same problem of shrinking products.

The source uses $10^{-400}$ for a 300-word email to show **underflow**: a value too small for a 64-bit float is stored as `0.0`. If both class scores underflow, they tie at zero again.

The solution is to use **log probabilities**:

$\log(a \times b) = \log a + \log b$

Instead of multiplying probabilities, take their logs and add them. Start with the log prior, then add one log likelihood per word. The logarithm keeps the ordering of the scores, so the class with the larger product also has the larger log score. The accumulated values stay at a manageable scale.



```python
def classify_log(message):
    words = message.split()
    score_spam = np.log(p_spam)
    score_ham  = np.log(p_ham)
    for w in words:
        score_spam += np.log(p_smoothed(w, spam_counts, len(spam_words)))
        score_ham  += np.log(p_smoothed(w, ham_counts,  len(ham_words)))
    return score_spam, score_ham, ("spam" if score_spam > score_ham else "ham")

s, h, verdict = classify_log(long_message)
print(f"log spam: {s:.2f}")
print(f"log ham : {h:.2f}")
print("verdict :", verdict)
```


**Saved output:**

```text
log spam: -40.44
log ham : -53.60
verdict : spam
```



The log scores are `-40.44` for spam and `-53.60` for ham. Spam still wins because `-40.44` is larger. A negative log score is normal: these probabilities are below 1, and the log of a number between 0 and 1 is negative.

This is why implementations use log space and why the model's word-probability attribute later is called `feature_log_prob_`.
